The run, step by step

1

Eligibility feeds

Every due config-driven eligibility feed is pulled from SFTP into its client staging table, then reconciled into the canonical dbo.eligibility — adding new members, updating existing ones, and terminating members who dropped off the file.

SFTP roster→ Eligibility_<Client>→ dbo.eligibility
2

MCR Hotels registry pipelineemails

MCR Hotels' roster and claims are imported and reconciled (eligibility + claims), then its reconciliation report is emailed to the AMT distribution list.

SFTP files→ staging→ dbo.eligibilityClaimsData_Prod
3

Claims loaders

Each client's monthly claims file is appended (add-only, so re-runs are safe) into its own ClaimsData_<Client> table — the raw, per-client record of every claim line.

claims file (.xlsx)→ ClaimsData_<Client>
4

Reconcile claims to productionemails

The new claim lines from each client table are normalized add-only into ClaimsData_Prod — the single table the app reads. Each client that had activity gets its own reconciliation email (claims added + eligibility adds / updates / terms).

ClaimsData_<Client>→ ClaimsData_Prod
5

GLP-1 → OnBase exportemailsbridge

Identifies GLP-1 members across all clients (full drug list, matched to eligibility for the Member ID) that are not already in OnBase, and emails the CSV to the OnBase load team as an action alert. Sends only when there are new records.

ClaimsData_Prod→ GLP-1, not in OnBase→ CSV → techsupport@
6

Coverage reportemails

Sweeps the entire SFTP tree and cross-references it against the active loaders and the processed-file log, so any folder or file without a working loader — or a new file not yet loaded — is surfaced. The summary is emailed to the distribution list.

SFTP tree scan→ weekly report email

Reconcile rules & what the app reads

Eligibility → dbo.eligibility

  • In file, not in eligibility → add (Active)
  • In both → update fields, keep Active (blanks never overwrite existing values)
  • In eligibility, not in file → terminate — set thru-date to the file date, mark Inactive

Claims → ClaimsData_Prod

  • Keyed on client + claim line (patient, service date, NDC, Rx, fill)
  • Add new only — existing prod rows are never changed or deleted
  • Cost columns carried through (Plan Paid / Gross Cost / Copay)

The app reads ClaimsData_Prod and dbo.eligibility — never the per-client tables. Every client flows the same way: client file → client table → reconcile → production.

The GLP-1 → OnBase step is temporary

Bridge until full app cutover

Step 5 exists only to keep OnBase fed with new GLP-1 outreach records while the old system is still in use. Once client contract & benefit setup lands in the new app — so any client configured for GLP-1 outreach gets the logic automatically — this weekly export to OnBase can be retired.
